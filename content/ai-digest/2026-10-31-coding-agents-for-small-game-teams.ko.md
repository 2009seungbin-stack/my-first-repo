10월 마지막 주에는 코딩 에이전트 소식이 하루에 몰렸습니다. 10월 28일 하루에 개인 개발자의 긴 회고 글, Android Studio 정식 버전, GitHub의 연례 행사 발표가 함께 나왔습니다. 셋 다 "에이전트가 코드를 더 많이 쓴다"는 이야기로 들리지만, 작은 게임 팀이 가져갈 교훈은 각각 다릅니다.

## 1. "재미있는 게임을 만드는 일"까지 에이전트가 들어왔다는 회고

**무슨 일이 있었나.** 개발자이자 블로거인 Simon Willison이 10월 28일 글에서, 2026년 10월이 코드를 읽지 않고 대화로 만드는 "바이브 코딩"이 게임 제작에서도 쓸 만해진 전환점이라고 주장했습니다. 그는 Claude Opus 5.5 덕분에 3D 모델링, 음악 생성, 특히 게임 디자인이 좋아졌다고 평가했습니다. 직접 만든 예로 2~4인 멀티플레이와 리플레이를 갖춘 실시간 전략 게임 Battle Drones(Apache 2.0으로 공개)와, 마을·지하 통로·약 15분 분량의 이야기가 있는 탑다운 RPG Emberwick을 들었습니다. 동시에 한계도 분명히 적었습니다. Emberwick은 퀘스트 진행을 막는 이야기 충돌 같은 버그를 잡느라 플레이테스트를 많이 거쳐야 했고, 그는 이제 어려운 부분이 "만들기"가 아니라 AI 없이는 나오지 않았을 새로운 게임 아이디어라고 봅니다. AI가 만든 그림·음악·글이 일부 플레이어를 불쾌하게 할 수 있다는 점도 인정했고, 이런 게임으로는 기존 게임잼에 나가지 않겠다고 밝혔습니다.

**게임 작업에서 왜 중요한가.** 한 사람의 경험담이고, 본인도 모델을 체계적으로 비교하지 않았다고 말합니다. 그래도 눈여겨볼 지점은 있습니다. 병목이 코드에서 **플레이테스트와 기획**으로 옮겨 갔다는 관찰입니다. 1~3인 팀에서 이 변화는 일정표를 바꿉니다. 프로토타입이 빨리 나올수록 "이게 재미있는가"를 확인하는 시간과, 에이전트가 만든 버그를 찾는 테스트 시간이 일정의 대부분이 됩니다.

**무엇을 하면 되나.**
- 에이전트에게 맡기기 전에 "재미의 기준"을 글로 적어 두세요. 한 판이 몇 분인지, 실패했을 때 무엇을 잃는지 같은 한 줄 규칙이 있어야 결과물을 판단할 수 있습니다.
- 퀘스트나 대화처럼 상태가 얽히는 시스템은 사람이 플레이 경로를 직접 확인하세요. 저장 파일을 몇 개 만들어 두고 매번 같은 지점에서 다시 시작하면 회귀 버그를 빨리 찾습니다.
- 출시할 게임에 AI 생성 그림·음악이 들어간다면 스토어 공개 항목을 미리 정리해 두세요. 이 부분은 같은 주의 정책 해설 글에서 따로 다룹니다.

## 2. Android Studio Rabbit 2 — 쓰던 에이전트를 IDE 안으로

**무슨 일이 있었나.** Google이 10월 28일 Android Studio Rabbit 2를 정식(stable) 버전으로 내놓으면서 "Bring Your Own Agent" 기능을 포함했습니다. 40개가 넘는 ACP 호환 코딩 에이전트 가운데 원하는 것을 IDE 안에서 고를 수 있고, 발표에는 Claude Agent, OpenAI Codex, Junie, Google Antigravity가 예로 나옵니다. 에이전트는 Android 에뮬레이터, 빌드 시스템, Logcat 같은 Android Studio 도구를 쓸 수 있습니다. 함께 발표된 기능으로는 Android 스킬 관리자, 프로파일러의 LeakCanary 작업에서 메모리 누수를 진단하고 수정을 제안하는 기능, 에이전트가 바꾼 내용과 커밋 예정 변경을 검토하는 AI Change Review가 있습니다.

**게임 작업에서 왜 중요한가.** 모바일 게임을 Android용으로 빌드하는 팀이라면, 에이전트가 **로그와 에뮬레이터를 직접 본다**는 점이 핵심입니다. 에이전트의 실수는 대개 "컴파일은 되는데 기기에서 깨지는" 형태로 나타납니다. 실행 결과를 보면서 고칠 수 있으면 사람이 로그를 복사해 붙여 넣는 왕복이 줄어듭니다. 팀원마다 쓰던 에이전트가 달라도 같은 IDE에서 일할 수 있다는 점도 작은 팀에는 실용적입니다.

**무엇을 하면 되나.**
- 에이전트에게 넘기기 좋은 일은 결과를 기계가 확인할 수 있는 일입니다. 빌드 설정 정리, 크래시 로그 원인 찾기, 메모리 누수 추적부터 시작하세요.
- 게임 로직의 밸런스 수치나 아트 에셋 파일은 에이전트 변경과 별도 커밋으로 나누세요. AI Change Review 같은 검토 화면에서 코드 변경만 따로 볼 수 있어야 리뷰가 쉬워집니다.

## 3. GitHub Universe — 여러 저장소에 걸친 에이전트 작업

**무슨 일이 있었나.** GitHub는 10월 28일 Universe 2026 기조 발표 글에서 Copilot 앱의 Copilot projects를 공개했습니다. 여러 저장소에 걸친 에이전트 작업을 병렬로 돌리고 진행 상황을 한곳에서 관리하는 기능입니다. 작업마다 모델을 골라 조합하는 Copilot Fusion도 소개했습니다. 수동 실행, 이벤트, 일정으로 시작하는 클라우드 자동화(automations)가 결과에서 배워 개선안을 제안하고, 사람이 검토해 승인하는 방식도 발표됐습니다. 가격 면에서는 GitHub Enterprise 고객이 별도 구독 없이 Copilot 기능을 쓰고 사용한 AI 크레딧만큼 내는 방식이 영업 채널로 먼저 열렸고, 셀프 서비스는 "곧"이라고 했습니다.

**게임 작업에서 왜 중요한가.** 인디 팀의 저장소는 생각보다 여러 개입니다. 게임 본체, 에셋 변환 스크립트, 웹 빌드나 랭킹 서버, 스토어 페이지 자료가 따로 있는 경우가 많습니다. 저장소를 오가는 작업을 한 번에 맡길 수 있다면 "스프라이트 시트 규격을 바꿨더니 변환 스크립트와 게임 쪽 로더를 같이 고쳐야 하는" 종류의 일이 줄어듭니다.

**무엇을 하면 되나.**
- 에셋 규격(프레임 크기, 시트 배치, 파일 이름 규칙)을 한 문서로 정리해 모든 저장소에 같은 내용을 두세요. 에이전트가 저장소를 오가며 일할수록 기준 문서가 하나여야 결과가 어긋나지 않습니다.
- 일정 실행 자동화는 "에셋 폴더 검사"처럼 실패해도 피해가 작은 일부터 붙이세요. 예를 들어 새로 들어온 스프라이트 시트의 크기가 규격과 맞는지 매일 확인하는 정도입니다.
- 규격을 사람이 먼저 눈으로 확인하고 싶다면 [스프라이트 시트 만들기](/ko/sprite-sheet-maker/)와 [스프라이트 자동 분리](/ko/sprite-slicer/)에서 실제 시트로 프레임 배치를 맞춰 본 뒤, 그 값을 문서에 옮기면 됩니다.

## 정리

세 소식을 겹쳐 보면 방향은 같습니다. 에이전트가 쓰는 코드의 양보다, 에이전트가 **스스로 결과를 확인할 수 있는 환경**이 더 중요해지고 있습니다. 작은 게임 팀이 이번 주에 할 일은 새 에이전트를 고르는 것보다, 빌드·실행·검사 명령을 한 줄로 실행할 수 있게 정리하는 것입니다. 그 한 줄이 있으면 어떤 에이전트를 쓰든 결과를 같은 기준으로 판단할 수 있습니다.
