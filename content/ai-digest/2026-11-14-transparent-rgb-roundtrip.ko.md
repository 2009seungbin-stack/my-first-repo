## 알파는 같고 RGB는 달랐습니다

직접 만든 반투명 PNG를 Nerulio의 실제 이미지 처리 코드로 읽고 저장했더니, 알파 64인 영역의 3,072픽셀 중 Chromium PNG는 2,679개, Firefox PNG는 2,882개의 RGB가 원본과 달랐습니다. 알파 값은 그대로였고, 각 RGB 채널의 최대 차이는 각각 2와 4였습니다. 이 수치를 눈에 보이는 화질 저하율로 해석해서는 안 됩니다. 측정한 것은 0~255 범위의 채널 값입니다.

이번 조건에서 PNG와 무손실 VP8L WebP의 출력 RGBA는 서로 같았습니다. 그러나 반투명한 원본 PNG의 RGBA까지 같지는 않았습니다. 원본 데이터를 그대로 보관해야 하는 작업에서는 저장 형식의 무손실 여부와 전체 처리 전후의 픽셀 보존을 별도로 확인해야 합니다.

AI 에이전트가 브라우저를 조작하고 수치 비교와 글 작성을 수행했습니다. 사람의 시각 평가나 게임 엔진 실사용 시험은 하지 않았습니다. 아래 자료로 숫자와 파일을 직접 비교할 수 있습니다.

## 무엇을 16번 비교했나

입력은 [불투명 패턴](/assets/editorial/2026-11-14-alpha-roundtrip/opaque-chart.png)과 [알파 단계 패턴](/assets/editorial/2026-11-14-alpha-roundtrip/alpha-chart.png) 두 장입니다. 둘 다 직접 만든 128×96, 8비트 RGBA PNG이며 CC0 시험 자료입니다. 알파 단계 패턴은 세로 네 구역에 0·64·128·255를 사용합니다. 0은 완전 투명, 255는 완전 불투명이며 64와 128은 그 사이입니다. 각 구역은 32×96, 즉 3,072픽셀입니다. 별도의 불투명 입력은 같은 RGB 패턴 전체를 알파 255로 둔 대조군입니다.

2026년 11월 14일, 실제 운영 소스 `522f177ee86ada4c3d548f915ef36a5124c6f8b3`에서 Chromium 153.0.8010.12와 Firefox 155.0으로 실행했습니다. 각 브라우저에서 관련 소스 네 파일이 그 커밋과 일치하는지 확인하고, 실행 전후의 배포 버전도 확인했습니다. 크기 변환이나 배경색 합성은 적용하지 않았습니다.

| 검사 | 새 캔버스에서 실행한 작업 | 조합 수 |
| --- | --- | ---: |
| 읽기 | 실제 `Im.decode` 뒤 `getImageData`로 RGBA 읽기 | 4 |
| PNG 대조군 | 읽기 검사 없이 실제 `Im.blobOf`로 PNG 저장 | 4 |
| 읽기 후 PNG | RGBA를 읽고 PNG 저장하여 관찰 영향 확인 | 4 |
| WebP | 읽기 검사 없이 품질 1.0으로 WebP 저장 | 4 |

두 입력×두 브라우저×네 검사로 16조합입니다. **새로운 화면 다운로드 16회를 뜻하지 않습니다.** 실제 페이지가 사용하는 함수를 직접 호출한 진단이며, 파일 출력은 Pillow로 독립 디코딩했습니다. 앞서 [변환 안내](/ko/image/convert/)에서 내려받았던 PNG·WebP 100 여덟 파일은 `native-` 접두사로 함께 담아 별도 획득 자료임을 표시했습니다.

## 원본과 저장 결과의 차이

아래는 알파 단계 입력을 PNG로 저장한 결과입니다. 이 시험의 WebP 100은 동일한 RGBA를 복원했으며, 컨테이너의 VP8L 이미지 데이터도 검사했습니다. 변경 픽셀은 RGB 중 한 채널이라도 달라진 픽셀을 한 번만 셉니다.

| 브라우저 | 알파 | 전체 픽셀 | RGB 변경 | 최대 차이 |
| --- | ---: | ---: | ---: | ---: |
| Chromium | 64 | 3,072 | 2,679 | 2 |
| Chromium | 128 | 3,072 | 2,295 | 1 |
| Firefox | 64 | 3,072 | 2,882 | 4 |
| Firefox | 128 | 3,072 | 2,691 | 2 |

알파 값이 바뀐 픽셀은 없었습니다. 알파 255 구역과 불투명 입력 전체 12,288픽셀의 RGB도 바뀌지 않았습니다. 예를 들어 좌표를 왼쪽 위 `(0, 0)`부터 세면, Firefox PNG의 `(32, 0)`은 원본 `(32, 160, 0, 64)`에서 `(36, 163, 0, 64)`가 됐습니다. 이는 RGB 채널의 수치 차이이며, 같은 크기의 지각적 색 차이나 화질 점수를 뜻하지 않습니다.

완전히 투명한 알파 0 구역에서는 숨은 RGB 3,072개 중 3,071개가 달라졌습니다. 그 값은 그 자체로 보이지 않으므로 위 표의 화질 문제처럼 합산하지 않았습니다. 보이지 않는 채널 데이터를 보관해야 하는지와 일반적인 화면 표시 품질은 다른 요구입니다.

## 읽기와 저장을 나누어 비교했습니다

저장 전 `getImageData` 읽기와 저장 후 파일을 나누어 보면 다음과 같습니다. 표의 숫자는 같은 3,072픽셀 중 원본 RGB와 달라진 픽셀 수입니다.

| 브라우저·원본 알파 | 캔버스 읽기 | PNG 저장 후 |
| --- | ---: | ---: |
| Chromium·64 | 2,679 | 2,679 |
| Chromium·128 | 2,295 | 2,295 |
| Firefox·64 | 2,304 | 2,882 |
| Firefox·128 | 1,535 | 2,691 |

Chromium에서는 읽기 결과와 저장 파일의 RGBA가 같았습니다. Firefox에서는 파일 출력과 읽기 결과 사이에도 추가 차이가 있었습니다. 따라서 모든 차이를 디코더 하나나 PNG 압축 하나의 문제라고 단정하지 않습니다. `getImageData` 역시 외부로 변환해 읽은 값이며 브라우저 내부 저장 비트를 직접 덤프한 결과가 아닙니다.

WHATWG HTML은 2D 캔버스의 투명색이 premultiplied alpha 표현을 사용하며, 이 표현과 일반 RGBA 표현 사이를 유한 정밀도로 변환할 때 불투명하지 않은 색에 정밀도 손실이 생길 수 있음을 설명합니다. 이번 관찰은 그 설명과 일치하지만, 브라우저 내부 구현을 추적해 특정 함수를 원인으로 확정한 실험은 아닙니다.

측정 자체가 출력을 바꿨는지도 비교했습니다. 읽기 검사를 넣은 PNG와 넣지 않은 PNG는 네 쌍 모두 파일 바이트까지 같았습니다. 이는 이번 설정의 대조군 결과이며, 다른 측정에도 관찰 영향이 없다는 뜻은 아닙니다.

## 해시가 다르다는 것과 픽셀이 다르다는 것

이번 진단의 파일 출력 12개는 각각 이전 화면 다운로드 자료와 디코딩한 RGBA가 같았습니다. 다만 Firefox PNG는 이전 획득 파일과 바이트 해시가 달랐습니다. 해시는 파일이 정확히 같은지 검사하고, 픽셀 비교는 디코딩한 샘플 값이 같은지 검사합니다. 서로 대신할 수 없습니다. 이번 자료만으로 PNG 바이트 차이의 내부 원인을 특정하지도 않습니다.

원본 보존이 목적이라면 원본 파일을 따로 복사해 보관하세요. 형식 변환이 필요하다면 [변환 도구](/ko/image/convert/)의 실제 결과를 원본과 비교하고, RGB·알파·해상도를 각각 확인하세요. 채널 값이 계약 조건인 데이터 작업에서는 자신의 입력과 출력으로 검사해야 합니다. 이 시험은 사진, 색 관리된 넓은 색역, HDR·16비트 이미지, 반복 저장, 텍스처 필터링이나 게임 엔진 불러오기를 평가하지 않았습니다.

## 파일과 숫자를 다시 확인하기

```text
python verify-alpha-roundtrip.py
```

이 명령은 로컬 파일만 읽어 해시, 픽셀 수, 채널 차이, 관찰 대조군과 VP8L 구조를 재계산합니다. 새 브라우저 실험을 실행하거나 획득 당시의 환경을 독립적으로 보증하는 명령은 아닙니다. [측정 JSON](/assets/editorial/2026-11-14-alpha-roundtrip/measurements.json)과 [방법·범위](/assets/editorial/2026-11-14-alpha-roundtrip/README.md)에는 운영 소스와 고정 절차의 커밋, 브라우저 버전, 파일 해시와 다시 획득하는 조건을 적었습니다.
