## Official sharing and rights sources checked 2026-09-28

- [Picrew terms](https://support.picrew.me/en/terms) delegate commercial and modification scope to each creator. Nerulio will use **only self-authored CC0 parts or independently documented CC0 parts**. No scraping, rehosting or derivative parts from Picrew/competitors. A source table with artist, canonical URL, license, date and SHA-256 is required for every raster/vector part and background. The chosen default pack should be one coherent style, not an arbitrary CC0 collage. Release the project's original parts as CC0 with an explicit grant. Users may use and sell exports commercially, but the tool cannot transfer exclusive ownership of CC0 source shapes, confer trademark rights, or certify rights for user-supplied backgrounds.
- [X Publish](https://publish.x.com/) and [X help on share buttons](https://help.x.com/en/using-x/add-x-share-button) document link-post controls. Use a user-initiated HTTPS `https://x.com/intent/tweet` link containing the encoded avatar settings URL and optional text. This shares a **link**, not a local PNG/GIF. Do not ask for X OAuth or imply that an image is attached.
- [LINE share URL](https://developers.line.biz/en/docs/messaging-api/using-line-url-scheme/) accepts percent-encoded UTF-8 text at `https://line.me/R/share?text=...` on mobile. [LINE Share button](https://developers.line.biz/en/docs/line-social-plugins/install-guide/using-line-share-buttons/) shares a webpage URL; the [official FAQ](https://developers.line.biz/en/faq) says it cannot directly share photos/videos. Label the control “Share link with LINE,” and supply “Save card” separately. The deprecated `line://` scheme is excluded.
- [Kakao JavaScript Share tutorial](https://developers.kakao.com/docs/en/tutorial/js-share) requires an owner-created app, JavaScript key and registered JavaScript SDK/web domains. Hide the Kakao button without that config; do not fabricate an app key. A public image URL is needed for a Kakao rich card and cannot be created from a local Blob by a static site. If only a generic public preview is available, say so.
- Per-avatar settings are in a URL query, while the output image exists only on the user's device. Most social crawlers do not execute the client-side composer, so **a unique Open Graph image for every query URL is impossible in the static, local-only architecture**. The 1200×630 downloadable card can be attached manually or passed to the native Web Share API with a File when the user explicitly initiates sharing and the browser supports files. Link intents show a generic site card. Do not promise per-avatar social previews without an approved dynamic hosting design.

The 16×16 composition grid is a deliberate visual constraint. Before approval, draw a representative head/hair/eye/outfit set and inspect it at 32/48/64; if those three outputs cannot show distinct facial features and palette ramps, increase the master grid using a pixel-aligned 48 base with **separate authored 32px variants**. Do not silently use noninteger scaling at 48px. Palette ramps use semantic indexed colors (outline, shadow, base, highlight) per part; no claim that global hue rotation preserves all colors. `Random` chooses compatible part/color combinations using a versioned catalog and xorshift32 seed, not “AI.” Show exactly which parts were randomized and allow undo.

## Architecture

- Add one canonical task page `/game/pixel-avatar-maker/` through `src/tool-registry.js`, `src/intents.js`, `src/task/registry.js`, messages, capabilities and quota. Keep it a one-screen composer (large preview, categories, Random, Export) with color, animation and share options in expandable panels. Follow the existing local task shell. Studio Pixel and UI Lab remain adjacent editors, not duplicated as the avatar-composer UI.
- Versioned `src/avatar/catalog.js` lists the authored 16×16 indexed part masks, anchors, z-order, names, compatible sets, palette swatches, source/license metadata, thumbnail IDs and motion variants. `src/avatar/model.js` is pure state, catalog lookup, deterministic PRNG, settings validation and URL serialization. No executable code or arbitrary URLs from the query. Unknown ids and excessive query sizes fall back safely with a visible explanation; v1 URLs remain replayable after catalog changes.
- `src/avatar/render.js` composites indexed layers on a 16×16 RGBA logical canvas. It creates pixel-exact PNG by nearest integer replication (32, 48, 64 and higher). Circular profile mode is **preview clipping**, with an optional circular-alpha PNG named separately so users cannot confuse it with the square avatar. The 1200×630 card embeds an integer-enlarged avatar (e.g. 16×20=320) on a branded local canvas and includes no network image.
- `src/avatar/worker.js` renders 4096 output and GIF frames off the main thread. GIF uses an exact indexed palette and LZW writer; the generic `src/core.js` GIF encoder's 3-3-2 quantization is not acceptable for the planned skin/hair ramps. Keep ≤256 colors including transparency and verify disposal/loop/delay independently. Do not generate fake motion by interpolating soft frames: blink swaps the eye part; breathing uses authored shoulder/outline frames, with a motion-off accessibility setting.
- Optional user background input accepts local PNG/JPEG/WebP via drag/drop, paste and picker; it is never uploaded or serialized in the URL. A share link reconstructs the built-in avatar and marks the local background as unavailable. It is the user's responsibility to have rights to the background. Built-in controls work without any file input.
- Output ZIP is optional for multiple sizes/frames; the primary button saves the current PNG. All processing remains client-side and no new fetch is made. A generic share card is downloadable; native Web Share file availability is feature detected after a user click. X/LINE/Kakao actions are separate user-initiated paths. The app must never suggest successful posting until the platform confirms it.

## Risks for coordinator review

1. **Artwork production is the quality bottleneck.** A small but coherent authored CC0 set may be better than hundreds of mismatched options. Review a representative sprite lineup before building all category permutations.
2. **Picrew rights are maker-specific.** No copied Picrew art and no assumption that Picrew's non-commercial maker output can seed our catalog.
3. **Share card versus URL.** A local 1200×630 card is not a dynamic OG preview for the query URL. X/LINE share a link; Kakao requires owner credentials/domain and may still show a generic public card.
4. **Commercial license language.** CC0 parts permit commercial reuse but cannot grant exclusivity or clear third-party marks. If the user adds their own background, the tool cannot assess its rights.
5. **Animation quality.** GIF palette/disposal must be measured, not inferred from a moving preview; accessibility motion-off preference must be respected.
6. **Performance/mobile.** 4096 output and GIF batch can exhaust constrained devices. Expose capped choices, progress/cancel and explicit measured limits; a target is not a verified result.
7. **Competitor scope.** Four products produced scoped files in this review; SquareFace.io paid exports and Picrew generated output remain UNVERIFIED. Do not claim paid parity until identical tasks and licenses can be compared.
