## 2. Decisions

### D1. Keep the existing stack; do not migrate to Astro/React
The site is 904 generated pages with a working SEO machine (hreflang, lastmod ledger, IndexNow, live
checks). Rewriting it in Astro would put every indexed URL at risk for no user-visible gain. New pages
are rendered by pure functions (`platform/render/*`) that run **both** in the Worker (SSR) and in Node
(tests). Browser behaviour is small "islands" in `src/platform/*` (follow button, vote widget, forms).

### D2. Database: Cloudflare D1 (SQLite) instead of Neon Postgres — deliberate deviation
The directive prefers Postgres/Neon/Hyperdrive/Drizzle "where migration is reasonable" and "existing
compatible service if already configured". We choose **D1**:

- the production build runs **without `npm install`** — Drizzle/pg drivers/esbuild are unavailable at build time;
- the repo already has a tested D1 service layer (migrations, atomic batches, local D1 E2E in CI);
- no new vendor account, no Hyperdrive, no cold starts; D1's free tier (5 GB, 5 M reads/day) covers launch;
- search: SQLite **FTS5 with the `trigram` tokenizer** gives the substring matching that pg_trgm would
  give, and it matches Korean/Japanese without a morphological analyzer (verified locally: "지포스",
  "4060" match). Queries shorter than 3 characters fall back to indexed alias prefix lookups.

Reversibility: all SQL lives in `platform/db/*` repositories (no SQL in handlers or renderers), uses
portable types (TEXT/INTEGER/REAL, JSON as TEXT), and no triggers. Moving to Postgres later means
porting those repositories and the migrations, not the product.

### D3. TypeScript strictness without a compile step
New code is plain ESM with JSDoc types and `// @ts-check`; CI runs `tsc --noEmit` with `strict: true`
over `platform/` and `server/platform/` (`tsconfig.json`). Production still serves/copies source files
directly, so the zero-dependency build keeps working.

### D4. Rendering and caching
Public entity, hub, radar, community and history pages are **server-rendered by the Worker from D1**
and cached at the edge with the Cache API (`s-maxage` + `stale-while-revalidate`); anonymous visitors
and crawlers are served from cache without a DB query. Personal modules (follow state, my votes, My
Radar) are separate JSON calls from islands, never baked into cached HTML. Writes that change a page
bump a per-entity version so the next request re-renders.

Directory pages that need no data (`/{l}/tools/…`, `/{l}/my/…` shells, `/admin/`) are **static** build output.

### D5. Everything new is behind `PLATFORM=on`
Like `SERVICE_API`, a build without `PLATFORM=on` is byte-for-byte today's site. With it, the build adds
the static shells, the new header/home, `_routes.json` entries for SSR prefixes and the v2 API. The
owner flips it after D1 is provisioned and seeded (`NERULIO_2_MIGRATION_PLAN.md` §4). Free/Pro
metering stays controlled by `SERVICE_API` independently; auth/sessions are shared.

### D6. Collectors run in GitHub Actions, ingest through the Worker
Pages has no cron. Collectors (`collectors/<source>/`) run on a GitHub Actions schedule (public repo →
free), fetch official APIs/feeds, keep the raw snapshot metadata, normalize, and POST observations to
`/api/v2/admin/ingest` (bearer `INGEST_TOKEN`). The Worker runs the one shared ingest pipeline
(match → diff → facts/changes). The same pipeline imports curated seed data and runs in tests against
the node:sqlite shim. Sources that cannot be automated legally/reliably are `MANUAL_SOURCE` and are
maintained in the admin console.

### D7. Auth
Reuse the existing Google OIDC flow and session model; add GitHub OAuth and Discord OAuth with the
same state/nonce/cookie handling (no new libraries in the Worker). Anonymous browsing everywhere; an
account is required only to follow, report, vote, edit, comment, keep a stack or get alerts.

## 3. One platform, five vertical modules

```
                ┌──────────── shared primitives (platform/) ─────────────┐
 Tools ───────► │ Entity · Alias · Relation · Fact(+scope) · Source ·     │ ◄── collectors/*
 (existing)     │ Snapshot · Version · Change · Event · Availability ·    │ ◄── seed data (data/seed/*)
                │ Compatibility · CommunityReport · RolloutVote · Follow · │ ◄── community (API v2)
                │ Stack · WikiRevision · Discussion · Comment · Flag ·     │
                │ ModerationAction · Reputation · AnalyticsEvent           │
                └───────┬───────────────┬───────────────┬─────────────────┘
          vertical config (platform/verticals/*.js): entity types, fact properties
          (labels, units, freshness SLA), relation types, report kinds, page sections,
          related tools, maturity label (LIVE/BETA/EXPERIMENT/PAUSED)
                        │               │               │
                 Entity pages      Radar feed      My Radar / Community / Search
```

A vertical is a configuration object plus optional renderers for its own page sections. Adding a
vertical = one config file + seed data + collectors; no new tables.

| Vertical | Entity types | Unique value loop (V1) |
| --- | --- | --- |
| AI | provider, service, plan, model, feature, runtime | model/feature → current availability & change → rollout vote |
| Games | game, translation_patch, developer, publisher | game → official Korean? patch? verified for which version → Works/Broken report |
| Hardware | gpu, vendor (+ ai models via AI) | GPU → specs, which open models fit (labelled estimate), community benchmarks → submit benchmark |
| Studio | app (DAW, Blender, Godot, OBS), plugin, vendor, os_release, audio_device | app/plugin → compatibility → upgrade preflight (web) |
| Subculture | franchise, work, character, creator, voice_actor, event, collaboration, merchandise | follow IP/character → upcoming events/releases |

## 4. Data model essentials (full schema: `docs/NERULIO_2_SCHEMA.md`)

- **Entity** ids are stable, readable keys `type:key` (`gpu:rtx-5070`, `game:steam-367520`,
  `model:claude-opus-4-1`). URL = `/{locale}/{vertical}/{slug}/`, slug unique per vertical. Merged
  entities keep a redirect.
- **Fact** = (entity, property, scope) → value, where scope = region × language × platform × plan ×
  app_version. Exactly one *current* row per scope; older rows get `valid_until` and stay forever.
  Every fact carries `verification` (OFFICIAL, AUTOMATED, COMMUNITY, COMMUNITY_VERIFIED, DISPUTED,
  UNKNOWN, ESTIMATE), `source_id`, `snapshot_id`, `observed_at` (last verified) and `confidence`.
- **Change** is written by the diff engine whenever a current value changes, appears or disappears
  (old, new, time, source). Radar, My Radar, history pages and alerts all read `changes`.
- **Regional overlays**: global entity, regional facts (`region='KR'`), no per-country copies.
- **Compatibility** (subject+version × target+version × environment → status) with a state machine:
  a new target version (e.g. a game update found by a collector) moves the current row to
  `UNVERIFIED_AFTER_UPDATE` until reconfirmed.
- **Community reports** never overwrite official facts. They feed a verification score (distinct users,
  reputation tier, recency, exact version match, contradictions) that can promote a compatibility row
  to COMMUNITY_VERIFIED or DISPUTED.
- **Rollout votes** (have it / not yet × country × plan × platform × app version) are aggregated and
  always labelled "community-submitted Nerulio reports (n)", never as population statistics.

## 5. Request flow

```
Browser ─► Cloudflare edge ─► Pages
   static: /src/*, /assets/*, tool pages, /{l}/tools/*, /{l}/my/* shells   (no Worker)
   _routes.json → Worker (server/index.js):
      /api/v1/*            existing account/quota API (SERVICE_API)
      /api/v2/*            platform API (PLATFORM) ─► platform/* ─► D1
      /{l}/(radar|ai|games|hardware|studio|subculture|community|search)/*
                           SSR ─► caches.default hit? ─► return
                                  miss ─► platform/render ◄─ platform/db ◄─ D1 ─► cache.put
      /sitemap-entities-*.xml  SSR from D1 (indexable entities only)
GitHub Actions cron ─► collectors ─► POST /api/v2/admin/ingest ─► ingest pipeline ─► D1
```

## 6. SEO rules for platform pages
- SSR HTML, unique title/description, self canonical, ko↔en hreflang (+x-default = en), OpenGraph.
- `index` only when an entity passes the content gate (`platform/seo.js`: enough sourced facts or
  relations or wiki text or community reports); otherwise `noindex,follow` and absent from sitemaps.
- Per-vertical sitemaps generated from D1; history/community sub-pages indexed only when non-empty.
- Related links come from real relations only.

## 7. Security & privacy
- Same-origin checks on every state-changing endpoint, no CORS, closed-field JSON bodies, size limits
  (existing `server/http.js` conventions); role checks for admin (`admin`, `moderator`, `curator`).
- User text is Markdown-subset → escaped HTML by our own renderer (no raw HTML ever passes); URLs are
  allowlisted schemes; images only via our R2 upload path.
- Collectors fetch only allowlisted hosts (no user-supplied URLs → no SSRF).
- Uploads (R2): MIME sniffed from bytes, size and dimension limits, re-encoded client-side to
  thumbnail/medium; no video, archives or binaries.
- Stack/preflight data is private by default; visibility per item is private/unlisted/public; the
  preflight API accepts only names/versions/formats, never paths, serials or file contents.
- Analytics: first-party, no third-party pixels; visitor key = HMAC of the existing anonymous cookie.

## 8. Analytics for choosing a vertical
Every event carries `vertical` (AI, GAMES, HARDWARE, STUDIO, SUBCULTURE, TOOLS). Events: page_view,
search_result_click, entity_related_click, tool_open, tool_complete, follow, unfollow, report_submit,
rollout_vote, wiki_edit, discussion_create, comment_create, share, preflight_start,
preflight_complete, return_visit. The admin dashboard shows per vertical: users, new users, traffic
source split, engagement, related-entity CTR, tool cross-navigation, 7/30-day retention, and
follow/report/share/contribution rates — explicitly not pageviews alone.

## 9. Future desktop scanner (not built in V1)
