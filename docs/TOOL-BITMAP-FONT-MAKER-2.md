# T7 — Bitmap Font Maker 2 design gate

Status: **design only; implementation awaits coordinator review**. Investigated on 2026-09-28 in `nerulio/tool-t7-bitmap-font`. This document separates observed competitor behaviour, documented capabilities, and planned Nerulio work. It is not a parity or release claim.

## User job and existing foundation

A game maker needs to draw or import pixel glyphs, tune baseline and spacing, prove that translated strings have coverage, and export files that the target engine actually loads. The existing `/game/bitmap-font-maker/` entry opens the **Font stage of UI Lab**, rather than an isolated duplicate editor. `src/task/ui-lab.js` already accepts a fixed grid sheet or local TTF/OTF, measures alpha bounds and advances, previews a line, detects some sheet grids, and exports `font.png`, BMFont **text** `.fnt`, `font.json` and optional SDF beta. `src/game/bmfont.js` is the pure font model, text writer/reader, and missing-glyph checker. `docs/UI-LAB.md` records independent text/PNG checks and Godot/Pixi results. The current checker does not read a TTF cmap. Existing font SEO content in `src/seo-depth/ui.js` is indexable; extend this one intent page and correct its format/engine claims as they become verified.

The existing `game/missing-glyph-checker` and `game/ui-scale-preview` remain views into the same Lab. Preserve their working state, character order, metrics and URL settings while adding editable glyphs. Avoid a second font data model. Source files and user-drawn glyphs stay local; a URL carries settings only.

## Official format decisions

- [AngelCode BMFont file format](https://angelcode.com/products/bmfont/doc/file_format.html): text/XML tags share `info`, `common`, `page`, `char` and optional `kerning` fields. Binary starts `BMF` + version **3** and typed little-endian blocks. Character IDs and kerning IDs are 32-bit in version 3. Validate signed offsets/amounts, counts, page references, texture bounds, and binary block sizes with an independent reader; do not treat our own writer/parser agreement as sufficient.
- [Adobe BDF specification](https://partners.adobe.com/public/developer/en/font/5005.BDF_Spec.pdf): parse `STARTFONT`, global metrics/properties and per-glyph `STARTCHAR`, `ENCODING`, `DWIDTH`, `BBX`, `BITMAP`, `ENDCHAR`. Preserve negative bearings, variable cell heights, and absent/non-Unicode encodings. Reject malformed row bytes with a line number. BDF input is monochrome; explain that colour and layers are not preserved.
- [OpenType glyf](https://learn.microsoft.com/en-us/typography/opentype/spec/glyf), [OpenType file structure](https://learn.microsoft.com/en-us/typography/opentype/spec/otff): trace each opaque pixel union into rectilinear contours, including holes, in font units. `TTF` means a TrueType `glyf` font; `OTF` output must be a conforming OpenType sfnt with a valid outline table, not renamed bytes. Prefer a license-audited local writer library after a minimal independent fonttools prototype. Test `cmap`, `glyf`/`CFF`, metrics, bounds, checksums, rendered pixels and installed-font load. A link to the [opentype.js project](https://github.com/opentypejs/opentype.js/) is a candidate, not a dependency decision or an output-quality claim.
- [Unicode Hangul algorithm](https://www.unicode.org/faq/korean.html) and [Unicode §3.12](https://www.unicode.org/versions/Unicode12.1.0/ch03.pdf): 19 choseong × 21 jungseong × 28 jongseong states (including empty final) = **11,172** modern precomposed syllables U+AC00–U+D7A3. The KS X 1001 target is **2,350** frequently used precomposed Hangul syllables; derive the exact set from an authoritative mapping and test count/hash before claiming coverage. Component placement cannot be a flat overlay: vowel orientation and final-consonant occupancy change the available zones. Draw and preview each component in its positional variant; let users override a generated syllable. Never claim typographic correctness from arithmetic coverage alone.
- Japanese presets: Hiragana U+3040–309F, Katakana U+30A0–30FF and optional user-chosen kanji. Do not silently promise all CJK ideographs in one atlas. Show exact requested/present/missing code points and texture-page estimates.
- [Godot BMFont import](https://docs.godotengine.org/en/stable/tutorials/ui/gui_using_fonts.html), [Phaser loader](https://docs.phaser.io/phaser/concepts/loader), and [Unity TMP font asset API](https://docs.unity3d.com/Packages/com.unity.textmeshpro@3.0/api/TMPro.TMP_FontAsset.CreateFontAsset.html): Godot consumes BMFont, Phaser's bitmap loader requests XML, Unity TextMeshPro needs a real source TTF/OTF converted to a TMP font asset. Engine guides must identify the verified path and exact version. No fake Unity asset file.

## Planned product surface

1. **Start:** open existing Font stage with “Draw glyph”, “Import sheet”, “Import BDF”, and existing “Bake local font file”. On a clean visit show a tiny editable sample with an honest “sample” label; no network requests. Select character by typing/paste, code point, or character map. The simple mode exposes cell width/height, baseline, preview text, and one export button.
2. **Editor:** nearest-scaled grid canvas with pencil/eraser/fill/rectangle, pointer drag, touch and keyboard arrow/space interaction; accessible label and focus, contrast, zoom. Guides: baseline, ascender, descender, x-height and advance. Edits are transactions with undo/redo and source-preserving import. Width and side bearings are per glyph; kerning is a pair table with an immediate specimen preview. Advanced controls are collapsed, with measured errors and reversible changes.
3. **Import:** local PNG sheet plus cell dimensions/order and explicit trim/alpha threshold; BDF with line-numbered diagnostics; optionally the existing TTF/OTF raster bake. Drag/drop, paste and file picker lead to the same import path. For arbitrary sheets, show a confidence explanation and allow manual mapping before mutating the project.
4. **Coverage:** paste or import translation text using existing `bmfont.js` extraction; report codepoint/missing count before and after export. Presets: ASCII, Latin-1, KS X 1001 2,350, algorithmic Hangul 11,172, kana, chosen kanji. Large presets are explicit confirmation and page/size estimate. Distinguish a generated glyph from a hand-corrected one.
5. **Export:** deterministic project JSON (for future edits), PNG atlas + BMFont text/XML/binary from one canonical metric model, TTF `glyf`, conforming OTF outline font, and a ZIP with only independently verified selected formats. Include Godot, Phaser and Unity TMP guides and a missing-glyph report. Exports must state page count, actual supported characters, transparent/monochrome limits, line height and license responsibility. The preview uses exported metrics; a reimport view shows the written files, not only the in-memory model.
6. **Locales/SEO:** all UI and errors ko/en/ja through `src/task/strings.js`; settings are in URL without glyph pixels or source data. Expand the existing one `/game/bitmap-font-maker/` SEO page with answer, mechanism, example, steps, troubleshooting, alternatives, limits, version/evidence and official links. Update sitemap lastmod and audit; no doorway variant.

## Architecture and compatibility

```
UI Lab Font stage (src/task/ui-lab.js, strings.js)
  -> project/undo + glyph bitmap editor (new pure model + canvas view)
  -> import adapters (PNG grid, BDF, existing local font rasterizer)
  -> canonical BM font object (extend src/game/bmfont.js without breaking v1)
  -> Worker: pack pages, Hangul composition, contour extraction, font writing
  -> exports: PNG + text/XML/binary; TTF/OTF; project JSON + guides
  -> independent test readers and real engine loaders
```

Use typed arrays for bitmaps, sparse glyph maps keyed by Unicode code point, copy-on-write transactions, and a versioned project schema. Keep the existing `gridFont`/`measuredFont` and v1 JSON behaviour for imported sheets; introduce v2 only where kerning, page IDs, edit provenance or CJK components require it. Do not force every existing page to load the font writer. Worker messages carry buffers with transfer, progress and cancellation; no SharedArrayBuffer is planned. If a future dependency requires isolation, place that work on an ad-free isolated route. Guard total atlas pixels, glyph count, contour count and worker memory before starting; provide a partial coverage report instead of an opaque crash.

Single-page PNG is the first compatibility baseline. Multi-page output is required for large sets if real engine import can be proved; otherwise mark a target engine/format unsupported at that set size and offer a smaller subset. An 11,172-glyph set at 16×16 uses **2,860,032** raw cell pixels before packing (11,172 × 256); this rough count excludes margins, pages, atlas dimensions and JS buffer copies. Benchmark actual bytes and time rather than equating this estimate to memory use. Unicode coverage is separate from legibility and shaping.

## Acceptance and independent quality gates

| --- | --- |

## Risks and review decisions

- **Font output complexity:** a valid TTF/OTF needs a correct contour orientation, hole handling, metrics, `cmap` and table checksums. Prototype and validate one ASCII font before offering either download in the UI. OTF may need a different writer path from `glyf` TTF.
- **CJK visual quality:** 11,172 generated codepoints can all exist while many shapes collide or lose reading clarity. Component templates need visual review and user overrides; coverage numbers alone cannot settle this.
- **Texture ceilings:** 2,350/11,172 glyphs may exceed a single page, especially on mobile or at 32px. Enforce measured limits, then decide multi-page per engine based on actual imports.
- **Cross-branch integration:** `src/task/ui-lab.js`, `src/task/strings.js`, `src/game/bmfont.js`, `src/seo-depth/ui.js`, `tools/lastmod-ledger.json`, build/SEO metadata and shared browser tests are likely integration touchpoints. Preserve the existing UI Lab and checker contracts.
- **Competitor evidence limit:** FontStruct required signup, AngelCode app was not executed, SnowB export bytes were not captured, and BitFontMaker2 BUILD did not yield a download in the probe. Do not claim output parity. A release comparison needs matched fonts, sizes, char sets, rendered samples and independent reopening.
