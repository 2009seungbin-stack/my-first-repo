# Character Counter Pro — stage 1 design, 2026-09-28

Status: **design only; coordinator review required before implementation**. Branch `nerulio/tool-t4-counter`, base `origin/main` `cd1e69a`. This document records observations, proposed behavior, test oracles, and unresolved platform rules. It makes no claim that Nerulio has shipped the tool.

## Need and product decision

The demand reports identify Japanese `文字数 カウント` as a promising query (Semrush estimate 1.22 million searches, with Rakko reported eighth); they explicitly warn that the estimate and top seven competitors were not verified. Korean application writing and English word count are adjacent user intents. One substantial `/character-counter/` task page with localized `/ko/`, `/en/`, `/ja/` equivalents is the proposed canonical family. There is no evidence yet for separate indexable variants. The page must explain count definitions; a number without its unit will mislead applicants.

The editor is local only. Text typed, pasted, dropped, or selected from a `.txt` file stays in browser memory and must not be sent in analytics, URLs, error reports, storage, or network requests. Only settings go into the share URL. No model or “AI” wording is needed.

## Hands-on competitor study

On 2026-09-28, I opened and typed/pasted the **same diagnostic string** into four live free tools: `A 한 😀\nＢ é` (`é` is `e` plus U+0301). This has 11 UTF-16 code units, 10 Unicode scalar values, and 9 extended grapheme clusters if LF counts as one. The deliberately mixed scripts, emoji, and combining mark expose differing definitions. Values below are the live UI values, not inferred implementations. JIKAZOO's paste alone did not refresh its result; an extra typed `x` triggered a count of 12, so its value for the original string is inferred as 11 and marked accordingly.

## Rules and technical design

* **Count units:** `Intl.Segmenter(locale, {granularity:'grapheme'})` is the human-facing default; show Unicode code points and UTF-16 code units in details for form compatibility. Unicode UAX #29 describes extended grapheme clusters, and JS segmentation can vary with the browser's ICU/Unicode version. Never call a JS `.length` value “characters” without its label. Spaces and line endings are separate filters. CRLF is one logical line break, while file byte counts reflect original bytes or the explicitly normalized editor text, never silently both.
* **Width:** Offer full-width/half-width counts and optional weighting separately from bytes. Define the exact East Asian Width property handling (ambiguous characters require a declared policy) and test ASCII, half-width kana, full-width Latin, combining marks and emoji. Do not equate display width with encoded bytes.
* **Encoding:** Native `TextEncoder` is **UTF-8 only**, regardless of a passed label. A local Node runtime probe produced `new TextEncoder('shift_jis').encoding === 'utf-8'`; `TextDecoder` accepted `shift_jis` and `euc-kr` but rejected `cp949`. Browser parity remains **UNVERIFIED** because a browser experiment using a `data:` page was blocked by the browser policy; no alternate execution route was attempted. Design a pinned, audited client-side encoding implementation (for example an independently verified bundled mapping), including explicit replacement/unmappable counts. Do not ship a number for Shift_JIS, EUC-KR or CP949 until the exact encoder and reference command (`iconv`/Python codecs) agree over a corpus. `euc-kr` under WHATWG can be an alias of the web's Windows-949-compatible encoding; **strict EUC-KR vs CP949 must be labeled and tested separately**, or collapse to one accurately labeled web encoding mode. Never infer byte length as 1 or 2 per script.
* **X:** Pin an official [`twitter-text` v3 config](https://github.com/twitter/twitter-text/blob/master/config/v3.json) and parser/conformance fixtures. Its config currently specifies scale 100, ordinary maximum 280, default weight 200, selected one-weight ranges, emoji parsing and 23-character transformed URLs. The published [config explanation](https://github.com/twitter/twitter-text/blob/master/config/README.md) shows why a naïve grapheme count differs. X says Premium longer posts can reach 25,000; show the ordinary-post meter as an estimate, not a posting guarantee. Retest current official config immediately before implementation and release. Avoid copying a few regexes and calling them official X counting.
* **Manuscript paper:** `ceil(non-space grapheme count / 400)` is only a simple Japanese 400-character *volume estimate*. A line-layout estimate must implement 20 cells × 20 lines, explicit newline consumption, and expose handling for punctuation, paired brackets, and vertical writing before claiming exact manuscript sheets. For Korean 200-cell paper, present the division estimate first and mark precise layout rule **UNVERIFIED** until an authoritative Korean source is found. Do not silently map grapheme count to paper cells for emoji/combining clusters.
* **Application forms:** No official Saramin/JobKorea help page establishing a universal byte or whitespace rule was found in this research. Both have counter entry points, but application limits are employer/form-specific. The UI should let users choose grapheme, code point, UTF-16, or verified byte unit; space/line inclusion; and a custom limit. Call these “custom application settings,” never “Saramin-compatible” or “JobKorea-compatible,” until the platforms' live counters and official help confirm that precise contract. A separate result comparison with their live tools is still needed.
* **Other metrics:** `Intl.Segmenter` word/sentence modes, with locale shown; paragraph = nonempty blocks split by one or more blank lines (also show physical line count); reading time is an adjustable words/minute or CJK graphemes/minute estimate with its rate exposed, not an exact promise. Script proportions use Unicode properties for Han, Hiragana, Katakana, Hangul and denominator defined as eligible letters, with mixed script/overlap policy. Duplicate phrases and forbidden-word findings are local, user-supplied or transparent deterministic suggestions, with a “dismiss” action and no automatic text rewrite.

## Page and integration plan

Use the existing single-task shell: register an intent and `TASK_TOOLS` entry, then a focused `src/task/character-counter.js` workspace with ko/en/ja strings following `src/task/strings.js`. Avoid a Studio workspace: this is writing utility rather than game asset editing. Initial view: large text box, visible primary count with unit, simple include-space toggle, custom target; below: clearly grouped application, SNS, manuscript, and linguistic details in collapsed sections. Each metric has a short “how counted” explanation. Text input, paste, `.txt` picker and drop converge on one state; reject binary/ambiguous encodings with an explicit decoding choice. Copy count/text, clear, undo/redo, and custom exclusions must be keyboard-accessible. Use native controls and visible focus; test 390×844 and 1440×900 screenshots.

Processing: main thread owns editor state and selection; worker receives a text snapshot with a monotonically increasing revision, returns counts and timings; stale results are discarded. File read, encoding, segmentation, script histogram and repetition scanning occur off the UI thread. For 1 MiB UTF-8 text, cap live refresh frequency and chunk expensive scans; preserve a responsive typing cursor. Worker creation failures need a documented bounded fallback or explicit failure, never a long blocking computation. No content-bearing URL, localStorage, IndexedDB or analytics payloads. Settings URL contains only count mode, whitespace options, language, target and reading rate. Undo history is memory-only, bounded, and is cleared on reload.

SEO: static indexable answer-first page with one canonical family and hreflang. Add localized `src/seo-depth/` `tool` entry covering count definitions, worked Unicode example, exact steps, troubleshooting, alternatives, limits and official sources; follow `docs/SEO-CONTENT-MODEL.md`. The editor works with JS, but the HTML must offer useful definitions and examples before JS. Update sitemap/lastmod and pass SEO audit at implementation stage. No keyword-only variants.

## Independent oracle and acceptance plan

1. Build a versioned CC0/public-domain or self-authored **real text** corpus: a Korean cover-letter-like paragraph, Japanese prose with ruby/quotes and line breaks, English essay, mixed-language copy, pasted HTML, and a public-domain literary excerpt with source/license manifest. Never include private real applications. Include exact byte files for UTF-8, CP949, Shift_JIS and malformed input.
2. For each string, calculate UTF-8 bytes via `TextEncoder` and independently via Python `encode('utf-8')`; legacy bytes via two independent encoders when possible (`iconv` and Python codecs), checking actual encoded hex and strict unmappable errors. Graphemes compare against Unicode GraphemeBreakTest plus a second ICU/regex `\X` oracle with version recorded. `twitter-text` official conformance YAML is the X oracle. Include repeated official URL, emoji sequence, invalid-character, and normalization cases.
3. Record same-input competitor observations separately from oracle values. Differences are expected where definitions differ; each table row names the unit, whitespace policy, newline normalization and exact input. For Korean job boards, capture live values and official policy before adding branded presets.
4. Test empty string, leading/trailing spaces, tabs, LF/CRLF, blank paragraphs, half-width kana, full-width Latin, Hangul Jamo, combining accents, regional flags, ZWJ families, variation selectors, unpaired surrogates, CJK extensions, URLs and HTML entities. Do not silently strip text.
5. Browser checks: worker stale-response order; paste, drop, file picker, IME composition, undo/redo, URL reload without text, no text network transmission, keyboard/focus and screen-reader labels. Validate desktop and mobile screenshots manually.
6. **1 MiB acceptance:** 1,048,576 bytes of real multilingual `.txt` (plus synthetic worst cases) on Chrome desktop and 390px mobile emulation. Measure 10 warm runs each: input-to-visible core count p95 ≤ 250 ms desktop / ≤ 750 ms mobile; keystroke input-to-next-paint p95 ≤ 50 ms; no long task > 100 ms during steady typing; peak memory and worker duration recorded, not guessed. A slower advanced encoding/repetition section may update separately with a visible pending state. Fail the performance gate if the editor loses input or returns stale counts. These targets are proposals until measured.

## Open risks and review questions

* The same mixed string produced incompatible counts and a suspicious Rakko UTF-8 value. Exact input normalization and byte algorithm need a reproducible second run.
* Browser-specific legacy encoding remains unverified; native `TextEncoder` cannot provide the requested formats. This is a release gate, not a nice-to-have.
* Japanese manuscript formatting and Korean manuscript rules need authoritative references. Until then, only explicitly labeled arithmetic estimates are supportable.
* Saramin/JobKorea byte and whitespace behavior is not established by their official help; branded modes stay out of scope until observed and sourced.
* X's current posting products can differ from the repository's v3 parser; expose config version/date and avoid implying account-specific posting eligibility.
* 1 MiB segmentation/repetition cost may require incremental computation. The budget is an acceptance target, not a measured result.
