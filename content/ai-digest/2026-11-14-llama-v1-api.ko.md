## 새 버전 소식을 내 코드의 질문으로 바꾸기

llama.cpp는 2026년 11월 13일 1.0.0을 공개하며 오래된 공개 API 삭제를 알렸습니다. 로컬 AI 기능을 넣는 앱이나 게임 플러그인이 C API를 직접 사용한다면, 업그레이드 전에 확인할 질문은 구체적입니다. **지금 쓰는 이름이 새 헤더에도 선언되어 있는가?**

Nerulio 메인의 수집 뉴스에서 연결한 공식 릴리스를 출발점으로, 0.9.0과 1.0.0의 헤더에 같은 작은 C++ 코드를 대입했습니다. 옛 이름 여섯 가지, 대체 이름 네 가지, 현재 API 대조군 하나를 각각 두 버전에 검사해 총 22회 실행했습니다.

AI 에이전트가 실제 컴파일러를 실행하고 결과를 정리했습니다. 별도 사람의 검토나 모델 실행 경험을 주장하지 않습니다. 이번 검사는 선언 확인이며 DLL 연결, ABI 호환성, 모델 로딩, 추론 속도는 측정하지 않았습니다.

## 어떤 입력으로 검사했나

태그 이름만 기록하지 않고 실제 소스 커밋을 고정했습니다.

- 0.9.0: `cd959bae99ff4bed22bef2604f45241c09bbb8c8`
- 1.0.0: `b1b770d90d94cad9e9ea5b993bdbc383a522fb28`

각 버전의 `llama.h`와 그 헤더를 읽는 데 필요한 ggml 헤더 여섯 개, 총 14개를 공식 저장소에서 받았습니다. 컴파일 전에 크기와 Git blob 해시를 확인했습니다. [측정 JSON](/assets/editorial/2026-11-14-llama-api/measurements.json)에 각 URL·커밋·SHA-256이 남아 있습니다.

환경은 Windows NT 빌드 26200, Python 3.10.11, Microsoft C/C++ 19.51.36256.0 x64, C++17입니다. Visual C++ 헤더 폴더는 14.51.36231, Windows SDK 헤더는 10.0.26100.0입니다. `/Zs`로 구문만 검사했으며 폐기 예정 경고를 오류로 바꾸지 않았습니다. 따라서 아래의 ‘통과’는 경고가 전혀 없다는 뜻이 아닙니다.

## 같은 코드가 어디서 달라졌나

| 검사 | 0.9.0 | 1.0.0 |
| --- | --- | --- |
| 현재 API 대조군 | 통과 | 통과 |
| 옛 모델 불러오기 | 통과 | 실패 |
| 대체 모델 불러오기 | 통과 | 통과 |
| 옛 컨텍스트 생성 | 통과 | 실패 |
| 대체 컨텍스트 생성 | 통과 | 통과 |
| 옛 모델 해제 | 통과 | 실패 |
| 대체 모델 해제 | 통과 | 통과 |
| 옛 어휘 수 조회 | 통과 | 실패 |
| 대체 어휘 수 조회 | 통과 | 통과 |
| 옛 warmup 설정 | 통과 | 실패 |
| 옛 defrag 필드 | 통과 | 실패 |

함수 검사는 이름의 주소를 참조하는 작은 코드입니다. 예를 들어 [옛 불러오기 검사](/assets/editorial/2026-11-14-llama-api/legacy-model-load.cpp)는 `llama_load_model_from_file`을 참조합니다. 0.9.0에서는 폐기 예정 경고와 함께 통과했고, 1.0.0에서는 C2065, 선언되지 않은 식별자 오류가 발생했습니다. [실제 진단 로그](/assets/editorial/2026-11-14-llama-api/v1.0.0-legacy-model-load.txt)를 확인할 수 있습니다.

같은 방식의 옛 함수 다섯 개는 모두 C2065로 실패했습니다. `llama_context_params`의 `defrag_thold`를 지정하는 [필드 검사](/assets/editorial/2026-11-14-llama-api/legacy-defrag-field.cpp)는 1.0.0에서 C2039, 존재하지 않는 멤버 오류를 냈습니다. 현재 `llama_model_default_params`와 `llama_batch_init`을 참조하는 대조군은 양쪽에서 통과했습니다. 헤더 경로나 표준 라이브러리가 통째로 누락돼 모두 실패한 상황과 구분하는 근거입니다.

## 프로젝트에서는 무엇을 확인할까

검사한 네 쌍은 다음과 같습니다. 대체 이름은 이전 0.9.0 헤더에도 이미 선언되어 있었습니다.

- `llama_load_model_from_file` → `llama_model_load_from_file`
- `llama_new_context_with_model` → `llama_init_from_model`
- `llama_free_model` → `llama_model_free`
- `llama_n_vocab` → `llama_vocab_n_tokens`

먼저 프로젝트와 네이티브 의존성에서 옛 이름을 검색하고, 0.9.0 헤더의 폐기 예정 안내와 새 선언을 함께 읽으세요. 이번 주소 참조 검사는 대체 함수의 모든 인자·반환값·수명 주기를 검증하지 않습니다. 호출부를 바꾼 뒤에는 프로젝트 자체를 다시 빌드하고 실제 로딩·해제 경로를 시험해야 합니다.

`llama_set_warmup`은 위의 네 쌍과 다릅니다. 옛 헤더의 안내는 사용자가 직접 warmup 실행을 하도록 권합니다. 임의의 새 함수 이름으로 치환할 근거는 이번 결과에 없습니다. `defrag_thold`를 설정하는 코드도 새 구조체 정의에 맞춰 검토해야 합니다. C API를 직접 호출하지 않는 HTTP 클라이언트의 호환성은 이 선언 검사로 판단할 수 없습니다.

## 직접 재현하고 범위 확인하기

[증거 ZIP](/assets/editorial/2026-11-14-llama-api/evidence.zip)에는 원본 검사 코드 11개, 로그 22개, 측정 JSON, 설명, 재현 스크립트와 입력 핀이 있습니다. [매니페스트](/assets/editorial/2026-11-14-llama-api/manifest.json)는 매니페스트와 ZIP 자체를 제외한 37개 파일의 크기와 SHA-256을 기록합니다. ZIP에는 그 파일들과 매니페스트, 총 38개가 들어 있습니다.

설정된 x64 Visual Studio 개발자 셸에서 압축을 푼 폴더를 열고 실행하세요.

```
python measure-llama-api.py --compiler cl --output ./new-evidence
```

출력 폴더는 새로 만들거나 비워 두어야 합니다. 스크립트가 고정 커밋의 공식 헤더를 받아 해시를 확인합니다. 컴파일러·SDK·상류 헤더는 ZIP에 재배포하지 않습니다. 원본 검사 코드와 스크립트는 CC0-1.0으로 제공합니다. 환경 구성과 사용 범위는 [README](/assets/editorial/2026-11-14-llama-api/README.md)에 있습니다.

이 결과로 확인한 것은 특정 Windows 컴파일러와 두 고정 헤더에서의 11개 선언 검사입니다. 새 DLL을 오래된 바이너리에 교체해도 되는지, 특정 GPU나 모델이 동작하는지, 더 빨라졌는지는 별도의 실행 검사가 필요합니다. 실제 프로젝트의 업그레이드 판단에서는 이 작은 검사와 프로젝트 빌드·모델 실행 결과를 함께 보세요.
